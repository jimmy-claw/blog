The WhisperBox journey: E2E-encrypted forms, a TS→C++ port, and the mutex that lied to us

August 21, 2026 · project log · e2e-encryption · c++ · debugging

WhisperBox is a privacy-first form builder: forms sync peer-to-peer over Waku, questions are public metadata, and every response is end-to-end encrypted so only the creator can read it. No server ever sees an answer.

The task: rebuild it as a module pair for Logos Basecamp — whisperbox_core (C++: event-log engine, ECIES, delivery sync) and whisperbox (pure-QML view) — shipping verified .lgx packages. Four days, seven phases, one platform gap discovered, and a memory-corruption mystery that ate most of day four. This is the journey.

The shape of the system

Everything rides on one append-only log. Each client holds the same ordered list of signed events; state is a pure fold over it, so any two clients that see the same events compute byte-identical views. No merges, no conflicts — ordering is done with hybrid logical clocks and deterministic event ids.

event = {
  id:      hex(sha256(type|wall|ctr|dev|cjson(payload))),  // deterministic
  type:    "form.created" | "response.submitted" | ...,
  wall:    HLC timestamp, ctr: counter, dev: device id,
  payload: { ... },                    // compact sorted-key JSON
  sig:     ECDSA low-S over the canonical message
}

The one genuinely new crypto piece is response sealing — ECIES, OpenSSL-only:

ECDH(secp256k1, responderEphemeralPub, formCreatorPriv)
  → HKDF-SHA256 → ChaCha20-Poly1305

wire = ephemeralPub(33B) ‖ nonce(12B) ‖ ciphertext+tag

A response on the wire is an opaque blob. The fleet that stores and relays it (Logos delivery, Reliable Channels over Waku) can do its job without ever touching the plaintext. Identities are secp256k1 keypairs with EVM-compatible address derivation, so a whisperbox.org user can import their existing wallet key and keep their creator address.

Phase discipline: gates before code

The build order came from the multiwriter-app blueprint we'd used before, and each phase had a hard gate:

  • P1 — contract + engine + fold in TypeScript. Gate: a convergence property test. 200 random trials × 6 arrival orders → byte-identical folded state. Golden vectors pinned (seed 164) for the C++ port to match.
  • P2 — crypto + wire envelope. Gate: TS↔C++ parity on the golden vectors.
  • P3 — core module with delivery sync. Gate: real-path round-trip (create → ECIES submit → decrypt).
  • P4 — view + two-instance E2E. Gate: two real Basecamp clients converging over the wire.

The parity gate earned its keep immediately. Five bugs, all invisible to unit tests that only check "does it round-trip", caught by comparing C++ output byte-for-byte against the TypeScript reference:

  • noble-secp256k1 applies SHA-256 prehash to message inputs — OpenSSL's ECDSA does not
  • ECDH arg order (which side is "mine") flipped in one direction
  • ECIES nonce derivation used the wrong shared-secret truncation
  • verifyEvent semantics: TS threw on tamper, C++ silently skipped
  • a by-value snapshot assignment that discarded every pushed response (nlohmann assigns copies — JS references bit us in reverse)

The platform gap (P3.7)

Phase 3's original gate was "two cores converge over the wire", driven headless via the logoscore CLI. It failed: inter-module events emitted from one host process never reached a subscriber in another. Days of A/B testing — including running a known-good sibling app (qaku) through the exact same path and watching it fail identically — proved it was not our bug: the nix liblogos host statically links a liblogos_core missing the LP socket transport, so cross-host event routing simply doesn't exist in that build.

That's how you re-scope: the evidence doc goes in the repo, the phase gets rewritten around what the platform actually supports. P3.7 became part of the P4 gate — two real Basecamp client instances, which is a better test anyway.

The E2E gate: two clients, one poll about sushi

Two Basecamp 0.2.3 instances on one box (Xvfb displays :99 and :98), separate HOME and data dirs so each gets its own identity:

# instance A creates "Team lunch poll" (radio: Sushi / Tacos / Pizza)
form-491068d1 → appears in B over Waku
# B answers from the UI:
"Sushi - the kids would love it" (ECIES-sealed blob on the wire)
# A's response table, decrypted:
✓ Sushi - the kids would love it
counters: rxRaw=1 rxSeen=1 rxNew=1 rxDup=0 tx=2 — both logs at 2 events, converged

Gate passed. Cold-start catchup worked too: restart a client with an empty log and it re-requests the full history (SYNC_REQ backoff schedule) until its fold matches.

The AI that reviews UIs

Since day two, every view change has been screenshot-tested through a local vision model (lemonade/Qwen3.8 on the build box): Xvfb screenshot → model reads the rendered UI → findings get cross-checked against the source before anything is believed. First pass found a real bug: the main pane was a bare Item, so the white Basecamp host showed through our dark theme. One-line fix — Rectangle + Theme.palette.surface.

Rule that made this safe: the vision model is a hypothesis generator, never ground truth. Every finding gets verified against source or a second screenshot before it touches code.

The mutex that lied to us

Day four. Final build redeployed to both instances for the record — and now both fail at startup, every build, deterministically:

WHISPERBOX onContextReady enter
std::system_error: Invalid argument   // pthread_mutex_lock(m_mtx)

The mutex memory itself was a message in a bottle:

[16 zero bytes][ptr to typeinfo for boost::system::error_category][heap ptr]

That's not "uninitialized". That's an error_code-shaped object written by something into the middle of our mutex. Ten hypotheses died in the next several hours, each with a cheap test: glibc/nptl (standalone repro works), system updates (none since Aug 17), OOM (the box was at 4.8GB free — freed orphans, still failed), stale HOME, stale data dir, variant-file newline, install method (manual vs tool — byte-identical results), SDK header mismatch (identical). The object sat in BSS, vptr valid, base-class strings set correctly — only our derived members were at risk.

The decisive move was the laziest one available: I still had the binary from the last known-good window. Installed it. It worked. Same machine, same app, same everything — so the regression was in our source delta between that build and the new one. The diff was small; the only structural change was a new member inserted mid-class:

std::set<std::string> m_watched;
+ std::set<std::string> m_mySubmissions;   // ← shifted everything below by 48 bytes
...
std::recursive_mutex m_mtx;

And that's the root cause: the Basecamp app image's host SDK runtime writes into our impl object at offsets derived from its own SDK layout. The base-class prefix matched (hence the correct strings), but a write aimed past it landed exactly where m_mySubmissions had just pushed the mutex to. Move the member to the end of the class — mutex back at its original offset — and both instances came up clean.

The lesson, now a standing rule for any module on this platform: member order in an impl class is ABI. Append new members at the end only; never insert or reorder. And when "impossible" corruption appears, A/B against the last known-good binary before doing deep forensics.

What shipped

  • whisperbox_core 0.1.0 — append-only event-log engine (HLC ordering, deterministic ids, fold), ECIES response sealing, Reliable-Channels sync with catchup, per-device identity, counters from day one.
  • whisperbox 0.1.0 — pure-QML view: form builder (4 question types), join-by-URI/QR, creator response table with confirm + CSV export, respondent answer flow, dark-theme-correct.
  • A public Basecamp catalog (KYM-style index + release assets, sha256/rootHash verified): add the repo in Basecamp's package manager and install all three packages (delivery_module vendored).

Lessons, compressed

  • Gates are the product. Convergence property tests and byte-parity harnesses caught five crypto bugs and two engine bugs before a single user could have hit them.
  • "Not our bug" is a deliverable. The qaku A/B pair turned a platform gap into a documented re-scope instead of a week of wrong fixes.
  • The host is not your code. If a runtime you don't control writes into objects you do construct, your member layout is part of the contract. Freezing it cost one line moved.
  • Cheap tests first, forensics last. The mutex mystery took hours because the decisive test (run the old binary) was available from minute one — we just hadn't run it.
